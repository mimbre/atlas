# Runtime enrollment and capacity-based assignment

Status: proposed architecture, revised against the exact root `review-findings.json` (F1–F11) for `dev2-enroll3-author-ack-20261114`, with the F12 binding correction from root `review-binding-findings.json` under `dev2-enroll-binding-ack-20261114`. Nothing here is implemented or authorizes deployment. Paths below are relative to `atlas/`. Only this design changes in this assignment; each implementation slice needs a separate assignment.

A person must be able to use several Runtime instances, including a laptop and mini concurrently, select an instance for work, and use Runtime locally without Server. Enrollment grants environment-specific admission to an instance; it does not create person authority, migrate history or authorize failover. Runtime-to-core connectivity must follow a private Tailscale route. Its concrete route and enrollment-operation authority require the evidence and decisions in section 10.

Capacity scheduling on existing agents is an independent first deliverable, S0. It schedules ordinary ownership turns and releases known completed or confirmed quiescent allocations without enrollment. Loss, silence, a missing report or lease expiry alone never establishes process exclusion. Uncertain work stays held while unaffected work continues.

## 2. Identity, responsibility and scope

| Identity | Contract |
| --- | --- |
| Physical host | Informational hardware/location label. A host may contain several Runtime homes, including in one environment. Hostname/IP/tailnet-device identity is not Runtime identity. No host registry is proposed. |
| Runtime instance | A lasting local ID generated once and stored in its home, independent of worker name, host and daemon PID. Each home has one instance; another home creates another instance. Copying a home/key is not a supported instance-creation operation. |
| Environment binding | `(environment, instance_id)` identifies its Server presence. Reuse the proposed `machine` record and wire machine name as the environment's routing alias for this instance, **not one physical host**. Store immutable instance ID; an alias cannot be rebound to another instance. |
| Person association | `used_by`: machine → existing person, one in this version; inverse lists that person's many Runtimes. Set through an authorized operation. This is selection/association, not permission to invite, approve, rotate, stop or transfer. `invited_by`/`approved_by` remain separate audit relations. Shared-instance users are deferred. |
| Incarnation | Fresh durable random ID per daemon ownership acquisition. Home ownership lock excludes local concurrent owners. Reconnect preserves the incarnation; daemon replacement does not. Execution authority binds an incarnation, not a socket/key alone. |
| Connection | Ephemeral socket generation. Verified reconnect may replace the same incarnation's socket without granting new execution authority. |
| Enrollment | One environment-specific grant to an instance, with its own ID and retained key history. Re-enrollment after a terminal grant makes a new grant, never reopens the old one. |
| Slot / worker | Existing agent record linked by `runs_on` to that instance's machine record. One unit of execution capacity, not a host, person or Runtime. Adoption preserves agent keys. |
| Allocation | One durable selection of a slot for work. A new allocation always has a new identity, even for the same item/run entry/slot. Retry of that allocation retains its identity. |
| Execution | Exact turn/attempt on one Runtime incarnation. Native admission, task outcome and physical termination are different evidence. |

Local instance ID exists before connectivity. Enrollment binds the same ID/home to its alias without replacing local turn IDs. Test/prod use separate homes, instance IDs, keys, processes, records and listeners even on one host. Instance/incarnation IDs are random 128-bit lowercase hex; aliases remain `^[a-z][a-z0-9]{0,23}$`. Lost-home recovery must reconcile old attempts; enrolling the same alias is not a takeover mechanism. A distinct replacement instance can exist while old work stays held.

Console lists a person's `used_by` instances with alias/ID/environment, host label, admission and reachability. Explicit selection pins the assignment route to an exact instance. Capacity selection instead persists whichever eligible instance/slot it picks. A pinned unavailable Runtime waits; changing an admitted allocation's instance uses section 7's explicit transfer. Person association is never inferred from provider login, approval or tailnet membership.

Goals: invite/approve without Fly secret edits/core restart; deterministic scheduling; standalone use; multi-Runtime person selection; preserved exclusion and uncertainty. Non-goals: automatic cross-Runtime transfer, remote Code, history migration, shared-provider quota allocation, new platform registries, hostile-host isolation, sign-in implementation or sandbox/ACL/credential changes. Provider login stays local. Two Runtimes sharing Codex login do not obtain independent weekly budgets.

## 3. Independent existing-agent scheduling (S0)

### 3.1 Selection

S0 uses configured Engine agents and core `capacity.pool: {agent: {machine, backends, models}}`. It needs no enrollment, used_by, Tailscale, approval role, key authentication or later incarnation protocol. Rollout establishes the existing one-home-per-legacy-machine ownership and agent configuration; it does not claim to make an uncontrolled second token holder safe. An unverified pool member stays unavailable. No token copying/takeover belongs to S0.

A capacity owner states allowed backend/model and optional `differs_from: <earlier step>`. Resolve the earlier backend from exact execution evidence; unknown waits. Apply capacity where a default owner would apply; preserve hand assignments as today. S0 explicitly refuses capacity owners on pass states. Later enrollment changes the slot source, not these release rules.

One Capacity process in the existing single core is the sole writer of `assigned_to` in capacity-owned states; the run writes no competing default. Multiple active scheduling cores are outside this version. Outside capacity states ownership remains as today. Queue by persisted entry time then key. A candidate slot needs its exact configured Runtime endpoint registered, a matching backend/model, no cannot_run, active allocation or unresolved admission/execution. Liveness qualifies new selection, never release. Hand assignments also consume capacity. Prefer compatible last-worker affinity, then warm when actually reported (none in S0), longest idle, then lowest key. Backend readiness/limits are not shared-account quota reservations.

### 3.2 Durable allocation and admission

Reuse the existing assignment record, not a registry. Add description-mapped Flow-only allocation sequence, current allocation and terminal receipts. Current allocation holds ID, run/entry/item, slot/machine route (instance/incarnation from enrollment), execution mode, backend/model, timestamps, phase, admitted turn/attempt and evidence references. The new ID is a digest of `(assignment identity, allocation_seq + 1)`. Increment/install in one conditional assignment write checking entry, empty active allocation/assignee and prior sequence. Never reset sequence on release or entry change. After a lost write reply, read and reuse the installed allocation.

Work/allocation identity and lifecycle projection are distinct parts of that record. For S9 passes, section 7.3 defines the immutable work binding used by the current-intent comparison, separately from phase, grant, admission-result and evidence projection. Normal progress of one allocation never changes that binding. This separation adds no pass/enrollment dependency or implementation prerequisite to ownership-only S0; its existing exact-allocation admission/release rules remain intact.

Terminal receipts preserve immutable binding, admission, closure, process result and release evidence. Keep append-only versioned structured receipts on the assignment; no truncation/reuse. For capacity-bearing assignments, refuse deletion/recreation that would erase sequence or receipts, including normal subject-cascade deletion, until a separate evidence-preserving retention operation exists. At a documented storage bound refuse further allocations with retention-required status. Archival is outside this version; storage pressure cannot silently erase safety evidence. Facts checks stored evidence and trusted writers, never live registry state. Model metadata supplies kind/field names to platform code.

Phases: `selected → admitting → admitted → closed → released`; `held` preserves the last proven phase/reason. Capacity alone projects these fields and assignee. Runtime supplies immutable evidence on the exact turn or typed reply, not phase writes. There is no atomic Facts-to-native transaction.

An Engine may not start capacity work merely because it sees assignee:

1. Its serialized admission path records an exact turn/attempt and immutable request digest as a capacity admission proposal on the existing turn, through the permitted `fact` path. Facts stamps immutable authenticated Runtime provenance, not a client-supplied origin. Add a mapped admission stage distinguishing proposal/reservation from confirmed native start; a proposed turn is not process-start evidence. Capacity reads that proposal, checks its trusted origin and binding, and conditionally records its one grant on the allocation with `admitting`. Runtime reads that same grant through existing Facts reads. Competing proposals fail; lost acknowledgments recover the exact fact/grant. No new general Bus request permission is needed for S0.
2. Before adapter start, Runtime durably reserves the exact admission, rechecks entry/ownership/grant, and serializes start against its local closure gate. Copy allocation ID to the turn. Unconfirmed native delivery queries the original admission; no second start from missing evidence. This capacity-only Engine/Turn extension is part of S0, independent of enrollment.
3. Capacity records an exact `closure_requested` control field on the allocation; Runtime observes it by read/reconciliation, not a general remote command channel. Closure runs through the same local serialized gate. It persists a closed tombstone, forbids delayed start/grant use even after restart, and reports closure and any unresolved in-flight start as exact immutable turn evidence. An acknowledged closure alone is not proof a previously admitted process stopped. Proposals with no native process are reconciled by this gate; existing orphan cleanup must not end them or create a replacement automatically.
4. Release requires that gate closure plus exact not-admitted or confirmed process evidence. A timeout or no-turn-yet Facts read cannot substitute. Paths unable to establish these proofs leave the allocation held. Ordinary non-capacity execution remains on its existing contract.

Persist the local capacity gate under the existing owning Runtime home, keyed by allocation ID, with immutable request/turn/attempt binding, reservation result, closed tombstone and exact process-owner evidence. Reuse CommandAdmissions/History persistence helpers where compatible; do not change Service's admission format implicitly. A bounded execution-local record is needed because a Flow grant alone cannot reject a delayed local start after restart; this is not another scheduler/registry. Sync reservation before adapter call and closure before acknowledgment. Missing/corrupt/indeterminate records mean held, not not-admitted. Native termination evidence records owner home, host boot identity, PID/start identity, group and confirmed end; adapter DOWN or Turn's current ended write is insufficient. Capacity-specific Turn handling waits/reconciles this evidence without altering stop escalation. Scheduling release never clears Service's stop latch: explicit local latch release is separate and starts nothing.

### 3.3 Release and restart

| Observation | S0 action |
| --- | --- |
| Exact execution completed, admission closed, owning Runtime confirms no owned process remains | Retain terminal evidence and release conditionally on current allocation ID/phase. A task outcome or legacy ended label alone is insufficient. Known safe completion keeps scheduling useful. |
| Selected work never started | Ask exact Runtime gate to close allocation. Release on durable `not_admitted + closed`, or confirmed quiescence if it had started. Start timeout triggers reconciliation, not release. |
| Link loss, expired lease, stalled Runtime, uncertain native start, orphan report | Hold route/assignee/allocation and original turn/outcome. Do not end it merely to make it schedulable. Reconcile original home/native process evidence. |
| Late confirmed completion after loss | Recover exact closure/process evidence, then ordinary release. Loss does not permanently strand known completed work. |
| State exit/handover | Persist pending handover barrier; close/reconcile old admission and process before replacing assignee or starting successor-state work. Do not overwrite unresolved ownership to force progress. |
| Delayed release/completion of old allocation | No-op on current allocation; retain historical evidence. |
| Core/Flow crash | Reconstruct occupied slots from assignments/turns/receipts and pending run writes; exact lookup before any new pick. Empty registry is not absence of execution. |

The release write retains receipt and clears active assignee/allocation together, checking exact binding. Retry of a completed release returns its receipt. Queue age stays with the entry. Affinity after release needs a new allocation, even on the same slot. Capacity serializes selection and finishes/reconciles pending writes before another pick; at most one active allocation occupies an item or slot. Executors must respect allocation admission, rather than rely on a transient free-slot read.

Pure functions compute candidates; no release function infers termination from elapsed time. Other free slots continue unrelated work while a lost slot is held. Workers' existing read permission governs a Waiting view: item/state/requirements, entered time, position and reason, distinguishing no-fit/busy from held admission/process uncertainty or pinned unavailable instance. Control reads Flow's projection over existing Bus; it owns no queue.

## 4. Enrollment records and one state writer

Reuse proposed foundation machine/enrollment plus existing person/agent/assignment/run records. The following fields/checks are proposed additions, not current capabilities.

| Fields | Writer/constraint |
| --- | --- |
| Machine alias, immutable instance ID, host label, used_by | Trusted Control creates these only from an authorized invite operation. Alias/instance binding never changes; existing person fact required. Control alone changes association through a separately authorized operation, never through an enroll frame. |
| Backend/model/version reports | Exact authenticated current Runtime incarnation; declared and observed models remain distinct. |
| Current execution incarnation, reconciliation hold and lost reason | Flow projects trusted acquisition/reconciliation input. Connectivity stays ephemeral in Bus. |
| Enrollment invite intent/digest/deadline, instance/person binding, inviter; verified_request | Trusted Control, narrow operation/sender rules. Initial state absent until Flow initializes invited. One uninitialized/nonterminal grant per instance. Never store invite plaintext. |
| Enrollment state/timestamps/reason and approved slot count | **Flow only**, including initial invited and invited→pending. Person answers and verified_request are inputs, never Control state writes. Final states never reopen. |
| Current public key/fingerprint and complete key_history | Initial request by trusted Control; Flow initializes the key projection before approval. Thereafter only narrowly authenticated Control rotation may atomically append history/change current key. State remains Flow-only. |
| Slot routing alias, runs_on, index, enabled/draining/disabled | Flow only after authorized approval/change/adoption and quiescence. Routing alias and relation must agree. No person direct edit of Flow fields. |
| Allocation/transfer projection and receipts | Flow only. Runtime provides exact evidence, separately from human authorization. |

Enrollment has of_machine and immutable person/instance binding, with invited_by/approved_by audit relations. Slots belong to the instance, not the enrollment/host. New keys are `<alias>-<index>`; adoption preserves old agent keys. Decrease drains before disable, never deletes; increase uses unused indexes or confirmed idle existing slots. Role agents such as coordinator stay outside capacity slots.

Lifecycle: invited→pending on verified request, or invited→expired on unused timeout/withdrawal; pending→approved/rejected by timely authorized person answer, or pending→expired on unanswered deadline; approved→revoked by authorized answer. Change slots retains approved with an authorized count/cutover input. Rejected/expired/revoked are final. No answer or role may assign an agent as enrollment approver.

Refuse deletion of machine identity bindings, accepted verified requests and enrollment/key history, including terminal grants. Otherwise alias recreation or deleted retired evidence could bypass the stated identity/key rules. No purge/archive operation is enabled in this version.

### 4.1 Invite consumption and lifecycle ordering (F11)

Choose Flow as sole lifecycle writer. Control writes an immutable `verified_request`, **not pending state**. This is a typed verification input distinct from human answers and the current human-choice capture path. Narrow Facts checks admit only the trusted enrollment handler sender; Runtime or client-supplied `by: flow` cannot submit it.

Request evidence contains version, stable request ID, semantic digest, original signed-body digest, redacted validated fields, signature/challenge verification evidence, environment/alias/instance/person/key/capacity/adoption/pair digest, and Facts acceptance timestamp/position. The exact body is verified transiently; persisted fields omit invite plaintext and retain its digest. This is trusted-handler verification evidence, not a claim that the signature can be reverified against redacted JSON.

After all signature/invite/field checks, Facts linearizes one conditional write: state invited, request empty, exact stored invite digest/binding, acceptance at/before deadline, no used or reserved key, immutable constraints intact. Every committed verified_request reserves its initial fingerprint immediately, before Flow initializes key_history; checks include those reservations across all enrollments as well as history. Initial projection may use only its own exact reservation once. The committed request consumes the invite, even before Flow projects pending. Facts must serialize/check this narrow operation against expiry/withdrawal; it cannot rely on a stale Control read.

Locally persist request ID before dialing. A fresh nonce may authenticate a retry with the same semantic digest (environment/alias/instance/person/key/capacity/adopt; exclude nonce/signature/plaintext code). Control first verifies the retry, then returns original status/pair code for matching ID/digest and invite binding. Changed body/ID conflicts; no second consumption or key replacement. No arbitrary name, pending/approved grant or terminal grant is changed by an unauthenticated frame.

Flow polls committed request, persists pending/initialization writes and completes them before further input. Timeout/withdrawal projection must fail if a valid request was committed by deadline. Timer/withdraw first makes request submission fail its state check. Flow rereads before timeout and Facts enforces the invariant too. Crash after consume but before pending replays projection; pending expiry uses request acceptance time, not delayed projection time. Timely prepared person answers win under existing run rules. Approval waits for key/slot initialization acknowledgments.

Invite creation uses an immutable authorized operation ID. Control conditionally creates the machine binding first, then the uninitialized enrollment/invite intent referring to it; Facts checks alias and instance-ID uniqueness and one open/uninitialized grant across aliases. Retries recover those exact records by operation ID/digest; changed binding fails. A crash between records leaves a non-executable machine with no grant and can only resume that operation or be explicitly abandoned. Flow discovers the enrollment, creates its run, and alone initializes invited. Show code only after invited acknowledgement. Crash before display leaves an unused invite that must explicitly expire/withdraw before another; plaintext is not recoverable from Facts. No broad Control access to Flow fields or Flow impersonation is needed.

## 5. Private route and enrollment protocol

### 5.1 Tailscale requirement; route deployment gated

Runtime dials a **private Tailscale-reachable Runtime Bus endpoint**. No public listener, public Fly TLS/proxy_proto service or public IP is assumed. Existing Fly WireGuard remains today's route until a separately authorized private route is demonstrated. No Fly/global/provider credential distribution is the default.

Candidate A: approved tailnet interface on the core reaching only the Runtime listener. Candidate B: an approved private gateway forwarding only that listener from tailnet to Fly private network. Neither is selected/deployed here. Prefer an existing approved endpoint if sufficient. A gateway needs a concrete missing reachability capability, named owner and restricted forwarding; it is not a generic routing platform. An internal Fly hostname is not automatically reachable from tailnet.

Evidence prerequisites: exact private endpoint/DNS/port per environment; device join/removal authority; demonstrated tailnet→Fly reach; Runtime/Control and test/prod reachability separation; route revocation; direct versus gateway hop protection. Tailnet membership is reachability, never enrollment/person authority. No Control listener becomes reachable just to enroll.

Retain authenticated encryption and endpoint verification: proposed v2 uses TLS 1.3 over that private route with demonstrated trusted hostname/certificate chain, owner/renewal and trust provisioning. No disabled verification or public fallback. A different secure transport needs a separate decision/contract. Explicit in-process/loopback tests may use plaintext; never auto-downgrade after failure. No global credential/trust copying shortcut.

One protocol per listener: private v1 stays unchanged during migration; private v2 rejects v1 and vice versa. Ping every 30 seconds/75-second silence may update reachability and trigger reconciliation with injected test clocks. Neither heartbeat nor timing grants transfer or proves stop. Source address is diagnostic from the actual route, not an authority supplied by a forwarded header. Registration replay is not execution acquisition.

### 5.2 Invite, request, pairing and approval

Proposed Go CLI: `atlas-runtime enroll --env <test|prod> --name <alias> --invite <code> [--adopt dev1,dev2] [--new-key] [--wait 15m] [--dry-run]`. Home supplies explicit environment and persistent instance ID. No new Python product code. Pure/fakeable probes measure CPU/performance cores, memory MiB, free disk, Runtime build, backend version/readiness and declared models, never copying login. Proposal is min(floor(performance cores/2), floor((memory GiB−4)/4), sum of configured ready-backend caps), clamped to 1..64 when a backend is ready, otherwise zero. Person may adjust; reported caps are not shared-account quota proof.

1. Authorized person invites exact alias/instance/used_by person. Generate 20 random RFC4648 base32 characters (100 bits), displayed once with hyphens; ignore case/hyphens on input. Facts stores SHA-256 digest and default 24-hour deadline only. A frame cannot create a machine, person or invite. Serialized stored checks prevent two open/uninitialized grants. Withdraw unused invite or expire; re-enrollment needs a new invite.
2. CLI creates Ed25519 key in the environment home using 0600/O_EXCL; refuse wrong environment. Proposed files machine.key and machine.key.next must already be inaccessible to workers before key use. Revoked keys are never reusable; new-key preserves old file locally as retired evidence. This design does not authorize changing today's sandbox.
3. Server speaks first with version 2, environment, random 32-byte nonce. Signed enroll body is a JSON **string**, so both languages sign exact bytes. Bind environment, alias, instance ID, associated person, stable request ID, invite, public key, capacity/proposal, adopt list and Runtime version. Signature: `"atlas-enroll-v1\0" || environment || "\0" || alias || "\0" || nonce || SHA256(body)`. No canonical JSON assumption; body digest covers all fields.
4. Trusted Control checks exact field inventory/bounds, environment, signature possession, invited binding, digest/deadline and all historical key fingerprints. Commit section 4.1 input only. Refusal reveals no finer record-existence detail. Identical authenticated retries recover exact consumed request, never another grant.
5. Pair code: first 12 base32 characters of SHA-256 of fixed vector encoding tagged atlas-pair-v1, covering environment/alias/instance/person/key, semantic request digest and ordered adoption list. Both sides compute/compare. Changing association, adoption or capacity changes it. Render validated values, never sender-written instructions.
6. Flow presents person-only pending To-Do with Approve(slot count)/Reject, identity/pair/capacity and adoption barriers. Default pending expiry 24 hours from accepted request. Approve checks existing person fact and exact operation authority, key initialization and section 8 quiescence. Approval activates the public key, sends no private secret. CLI retries signed hello with bounded backoff until wait deadline; early exit leaves durable state.

Keep conservative shared Go/Elixir bounds and vectors: pre-auth line 8 KiB, response 5 s, max 64 concurrent pre-auth connections and bounded per-source attempts. Environment test/prod; alias pattern in section 2; public key standard base64 44 chars/32 bytes, signature 88/64; IDs 32 lowercase hex; existing person key ≤64 printable ASCII chars. CPU 0..1024 (cores >=1), memory MiB 1..16777216, disk MiB 0..2147483647; ≤8 unique backends, ≤32 models total, ≤32 unique adopt keys, slots 0..64, Runtime version 1..64 printable ASCII. Backend name `^[a-z][a-z0-9_-]{0,15}$`, version 1..40 non-space printable ASCII; models `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,63}$`; adopt keys `^[a-z][a-z0-9-]{0,31}$`. Clip measured numeric overflow/drop invalid strings with warning; server still strictly validates. Dry-run measures/validates without key generation/connection. Fix shared vector bytes and field table in implementation before interoperability claims.

### 5.3 Authentication and execution incarnation

Hello proves current enrollment key with distinct atlas-link-v2 tag over environment, alias, instance ID, fingerprint, incarnation and nonce using fixed vector encoding. Kind-free Bus verifier reads Facts through Control/model mapping. Register connection in machine index **before** second approval/incarnation verification; welcome only after that verification. Its explicit mode is execution-holder, reconciliation-only candidate, or management-only; a first/new incarnation may receive candidate mode with no execution authority while acquisition is pending. Revoke either wins the second read or drops the indexed connection after acknowledged write. This preserves the sound register/reverify race closure without making initial acquisition impossible.

Authentication initially permits reconciliation only, not new execution. First execution incarnation is acquired by conditional Flow projection after proving no prior active owner/admission. Same-incarnation reconnect proves local ownership record and recovers exact admissions before new work; it replaces only that incarnation's socket generation. Frames carry session generation; stale active writes/admissions fail. Explicitly correlated late evidence is retained historically under its old execution, never applied to a new allocation.

An incarnation string alone is not reconnect proof. The local acquisition record binds canonical home, host boot identity and daemon process start identity; only that still-owning process may reconnect as that incarnation. Copying a home or restarting a daemon produces a different acquisition and must take the replacement path. Recovery must reconcile every prior admission before granting any new work, and may not infer another host/home's process absence from its own process table. These are trusted-Runtime checks, not hardware attestation against a malicious stolen-key holder; compromised-host honesty remains outside the stated isolation guarantee.

Different incarnation with same identity/key is a collision/replacement request. Keep existing execution holder, alert, give newcomer no execution admission or orphan-cleanup authority over old turns. Replacement requires prior admission closure and confirmed quiescence of every exact prior attempt before Flow advances durable incarnation. Unknown processes keep the instance held regardless of socket/key/lease changes. Real daemon restart proves prior owned groups gone using persisted process identity/restart evidence; an empty new process table is insufficient.

Facts and admission receiver check authenticated sender plus exact environment/instance/enrollment/incarnation/allocation/turn/attempt against durable holder; reject stale renewals/mutations/admission. A logical incarnation fence cannot stop effects in an old process; quiescence remains necessary before successor authority. Core restart restores holder and reconciles, never grants a replacement because registry is empty.

Rotation uses a **management-only** authenticated connection bound to instance/grant; it neither replaces execution socket nor acquires incarnation. This changes the previous rotation-by-link-replacement proposal. Alerts diagnose collisions but do not enforce exclusion or revoke automatically.

## 6. Complete key history, revocation and security

No key registry: retain append-only version-1 key_history on each enrollment, entries `{sequence, public_key, fingerprint, previous_fingerprint, operation_id, accepted_at, verifier_evidence_digest}`. First entry comes from immutable verified request; each rotation appends. Successor entry retires predecessor; terminal enrollment state removes remaining authority. Entries cannot be removed/reordered/rewritten. Facts ordinary list/incoming checks can see K0..Kn after any rotation or re-enrollment. Refuse any fingerprint already present in history or reserved by a verified_request anywhere in this environment, including this grant. Recover an exact existing operation before attempting a new append; retry is not a new use. Failed/incomplete lookup refuses. Public history is not a retired private-key file.

Rotation proves old+new key possession with atlas-rotate-v1 label, binding environment/alias/instance/enrollment/operation ID/nonce/raw new key. One conditional enrollment write appends history and changes current key/fingerprint together, checking approved state, old fingerprint/history and no reuse. No lost secondary audit write can forget a key. Concurrent revoke/rotate: rotate-first retains history but loses authority on revoke; revoke-first refuses rotate. Identical operation replays its receipt, changed body conflicts. Regenerate alerts from durable history.

CLI creates .next with 0600/O_EXCL before request and atomically renames after ack. Lost reply/rename queries exact rotation operation using either locally retained key through restricted recovery handshake: only that operation's status, no execution/restoration of retired authority. If .next is current, finish rename. Network failure is not key-status evidence. At a documented history entry/byte bound refuse rotation/new grants, never trim history; archival/expansion needs separate design. Re-enrollment cannot bypass retired-key checks.

Revoke is an authorized input; Flow writes revoked and reconciliation hold. Control drops indexed links after Facts ack, with the hello double-check above. New admission/selection stops immediately. **Revocation does not stop old processes**, end turns, clear allocations or start replacements. Requesting stop through an authorized available channel records requested/signalled/confirmed separately; unreachable remains unknown.

Runtime key permits only its own endpoints and narrow runtime facts. Check current instance/incarnation and own turn/worker before execution evidence, cannot_run or backend/model/version writes. Never permit enrollment state, authority, Flow allocation projection or other instance writes. Platform modules use model mappings. No generic request tunnel is introduced. Existing atlas broker retains its current trusted Control path; moving it over the link is a separate authority-reviewed assignment, not a prerequisite for S0/enrollment.

Until separately implemented read scoping, linked Runtime retains today's Facts read surface; do not claim assignment-only reads. Stolen key can impersonate/forge its permitted results and read that surface; incarnation checks cannot prove a compromised host honest. Gates/person review and revocation remain necessary. Tailnet, enrollment, provider login, Code access and Control person operations remain distinct.

Key activation requires evidence that existing worker isolation denies the chosen home/key paths. If absent, a separate authorized sandbox assignment is required first. No credential/provider-session copying, Code token delivery or weakened sandbox/TLS belongs here. Separate environment signatures/invites/homes/listeners prevent test/prod reuse.

## 7. Loss, explicit transfer and immutable passes

### 7.1 Stop versus confirmation

Lost markers index durable reconciliation, not release authority. Flow records loss/revoke and enumerates held allocations after restart. Runtime may close local input and request one SIGINT on loss under its established stop policy, recording requested, signalled/error and confirmed termination separately. No proposed loss timer converts operator stop to kill or labels it stopped. Existing parent-loss/natural-completion cleanup remains a distinct mechanism; it is not a transfer authorization or a stronger operator stop. New kill/external fencing requires explicit authority/evidence. Half-open/stalled Runtime may miss timers; exclusion cannot depend on comparing clocks.

Known-completed/quiescent allocations use S0 release. Unknown native/process/effect outcomes stay with original allocation/attempt. Confirmed termination does not resolve unknown external effects: reconcile whether the specified successor operation is safe, or hold. Guidance/receipts remain on original execution. Unsealed folders/native sessions stay at source for explicit salvage, never automatic submission.

### 7.2 Explicit transfer protocol

Transfer is an explicit typed coordinator-authorized operation, not loss handling, laptop fallback or automatic policy. Record ID, actor/authority evidence, item/run/entry, exact source instance/incarnation/slot/allocation/turn/attempt/admission digest, exact destination instance/slot, immutable input manifest/digest and permitted new operation. If coordinator authority is not established, section 10 gates it; role aliases do not supply it.

Store versioned transfer payload/receipts in existing run pending protocol and assignment reference, Flow-only. Persist each stable outbox operation/digest before sending and ack evidence before advancement. Run cursor is authoritative over partial assignment writes; replay conditional projections before dispatch. Carry closure/query/preparation intent through exact assignment/run facts and authenticated Runtime evidence where sufficient. Any new direct Runtime request requires a separately specified, narrowly permitted class and authority check in S8; current Bus does not allow arbitrary requests. No generic request tunnel or distributed transaction is assumed.

| Phase | Evidence to advance |
| --- | --- |
| requested | Authorized immutable operation/exact source binding; same ID/body replays, changed body conflicts. Freeze new source allocation admission. |
| source_closing | Exact gate closes input/admission with tombstone and reconciles in-flight start. Stop only if authorized/required. Query original admission/result; unknown is not redispatch permission. |
| source_quiescent | Durable closed gate plus confirmed group termination, or exact not-admitted proof. Preserve unknown external effects; explicit reconciliation must show this successor operation safe. Lease, disconnect, revoke or destination's empty process table are insufficient. |
| destination_prepared | Destination admitted/free/eligible; local verification of sealed snapshot/revision/base or packet bytes/digests, scope/backend/model. Snapshot ID alone does not prove its local Code/cache has bytes. Missing bytes keeps source closed and transfer pending. No remote Code/credential transfer is assumed. |
| successor_committed | Retain source receipt and provenance; install a new allocation sequence/ID and fresh turn/attempt. For passes take explicit successor-entry transition below. Finish pending projections before dispatch. |
| destination_admitted / completed | Exactly one gate admits successor under stable identity; lost reply queries same admission. Another destination attempt needs another explicit operation, never a timeout redirect. |

Restart/disconnect resumes exact phase by lookup. Source reconnect before quiescence reconciles original attempt and starts nothing new. After successor commit old incarnation/allocation cannot reclaim ownership; late proof stays historical. Destination loss before admission waits; uncertain destination start stays held. Cancellation before commit may leave source closed: resuming needs new explicit admission, not erasing tombstone. Moving back after admission repeats protocol in reverse. Salvage cannot mutate frozen source request.

### 7.3 Passes: one admission owner and immutable successor (S9)

S0 refuses capacity passes. In S9 choose **pass execution instead of ownership-turn execution** in pass states: Engine excludes them from both starts and orphan reconciliation; pass receiver alone proposes pass admission. For enrolled capacity slots, ownership and pass proposals share Service's serialized slot admission/latch before any native start. Engine becomes ownership proposer, not second native admission owner. Adapt ownership execution to that existing Service gate in bounded S9a; drain/reconcile prior Engine turns before cutover. Do not enable passes while Engine can launch independently for that slot.

**Immutable work binding versus lifecycle projection (F12).** Freeze only after allocation, before receiver admission, using a versioned, description-mapped work binding. Its explicit fields are environment, run/entry/activity identity, subject and assignment identities, allocation ID/sequence, execution mode, owner/slot, Runtime alias/instance/incarnation, backend/model, and the execution-affecting input contract: instruction bytes/digest, subject fingerprint specification/value, permissions/scope, repository/base/snapshot or packet identity/digest and any other declared pass-request inputs. These fields and the full executable request become immutable for that intent. Use an explicit field inventory, not “all assignment values except phase”; an unmapped execution-affecting input fails validation until classified. Derive the current binding from actual assignment owner/route/work inputs and check it against the stored allocation binding, so retaining an old binding field cannot hide a genuine owner/route/input change.

Lifecycle projection includes phase, grant/reservation status, write-once proposed/admitted turn/attempt, completion/result evidence, closure_requested, hold/termination state, timestamps and receipt references. These are allowed to evolve under the existing authenticated transition/evidence rules for the **same** allocation; they are not part of current-work-binding equality. Newly reported turn/attempt is exact admission evidence bound once to this allocation and original request, never an extra executable input that requires refreezing. A second/conflicting turn/attempt or a mismatched evidence digest is still refused/held, not ignored as harmless lifecycle change. A completion observation may project `completed` while closure, result consumption and release remain separate facts; it proves neither safe replay nor automatic transfer.

Keep the original full assignment as immutable audit evidence if included in the frozen request, and keep its bytes in that request's original digest. Never refresh this audit copy, the request, digest or pass ID from a later lifecycle projection. The current-work check compares the explicit work binding and actual owner/route/input fences, **not full current assignment equality with the audit snapshot**. This is a required S9 change to today's `activities/pass.ex:46,58-63` and `runs/store.ex:903-916,938-945`, which currently freeze/compare all assignment values/links before polling. The distinction must apply to the subject fingerprint too: fingerprint only declared work inputs, excluding lifecycle projection, while still fencing genuine subject/input changes. Non-capacity passes retain their existing contract; capacity passes stay disabled until this S9 contract is proven.

With unchanged work binding, selected→admitting→admitted→completed progress, grant writes and added evidence must not block polling, exact admission lookup or consumption of a valid result. Admission eligibility remains a separate gate: held, revoked, closed or superseded authority can forbid new native start without forbidding read-only recovery of the original admission/result through an already authorized recovery path. This grants no revoked credential bypass, new remote read permission or authority change. A genuine work-binding change blocks current-result application and new admission until the successor protocol; it does not erase the original intent or forbid authorized historical lookup. Lookup/retry retains the original frozen request/ID/digest and original receiver, never resolves to the new route. Historical lookup is read-only; retry that could admit work still requires exact not-admitted evidence and current eligibility. Accepted-but-unanswered or indeterminate admission reconciles exactly; no changed request or replacement start is constructed from current lifecycle fields.

For capacity passes, retain the allocation/owner binding through result collection: Capacity may record completion, closure and process evidence, but cannot clear/reassign that allocation merely because the process ended. First the run durably records the validated exact pass result (or the explicitly reconciled terminal receipt) and its consumption/outbox progress. Only that consumption receipt plus section 3's closure/process evidence permits conditional release and subsequent ownership/entry handover. Recover a crash before the receipt by querying the same frozen pass; after the receipt, replay pending run writes/release without reapplying the result. This S9 release barrier prevents normal completion from invalidating its own pending pass by clearing its owner before collection. S0's ownership-only release has no new pass-consumption dependency.

Changed work binding cannot reuse `(run, entry, name)` ID. Ordinary phase/grant/evidence progress of the same allocation requires neither a successor entry nor another allocation. A genuine owner/route/instance/incarnation/allocation/input change follows the existing explicit successor protocol: after authorized source reconciliation/quiescence, archive old intent/admission/reply/transfer result as an immutable activity receipt in run history. Take explicit versioned self-transition that **increments entry**, retaining predecessor and successor plan. Dedicated successor-entry handling installs that plan without replaying unrelated entry side effects. Guards require old pass/outbox reconciled/archived; clear old pending pass only together with receipt. Freeze new allocation under `(run, new entry, name)`. Unsupported transition blocks instead of mutating frozen binding.

Persist cursor/pending writes before dispatch. Crash after entry advance replays allocation projection; crash after acceptance queries same admission. Stale old reply cannot advance new entry, only historical evidence. Expanding pass permissions to materialized-folder needs separately assigned receiver/profile validation and verified destination scope; enrollment alone does not authorize it.

## 8. Adoption and rollback
